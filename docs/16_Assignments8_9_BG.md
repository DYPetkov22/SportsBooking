# Задания 8 и 9 — реализация и проверка

## Анализ на първоначалния проект

Проектът е ASP.NET Core MVC, .NET 9, Razor и EF Core със SQL Server. `SportsBookingContext` обслужва бизнес данните, а `IdentityContext` — отделната Identity база. CRUD контролерите използват контекстите директно. Има услуги за файлове и отчети. Създаването и редактирането на резервации вече имаха Serializable транзакции. Плащанията проверяваха за съществуваща резервация и дублиране преди отделен запис. `SportsBooking.Tests` беше отделен xUnit проект с Moq, но без референция към приложението и само с празен тест.

## Задание 8

- Съществуващите транзакции при резервации са запазени. Обработените грешки се логват, а неуспешната транзакция се освобождава преди повторното зареждане на формата. EF освобождаването връща непотвърдената транзакция назад и обработва и вече прекратена от SQL Server транзакция.
- `PaymentService.SaveAsync` започва EF Core Serializable транзакция **преди проверките**, проверява резервацията и уникалността на плащането, записва и потвърждава. При невалидна връзка, липсващ запис или изключение няма commit. `await using` освобождава транзакцията и осигурява rollback. Съществуващият уникален индекс остава последна защита срещу дублирано плащане.
- Единичните останали `SaveChangesAsync` операции използват автоматичните EF Core транзакции. Не са добавяни излишни ръчни транзакции около единични записи. Регистрацията използва две отделни бази и запазва съществуващите компенсиращи операции; не е въвеждана разпределена транзакция.
- `ErrorHandlingMiddleware` прихваща необработените изключения във всички среди, записва изключението с път и идентификатор на заявката и изпълнява MVC страницата за 500 със статус 500. Не разкрива stack trace на клиента. При проблем в самата страница има безопасен HTML fallback. При вече започнал отговор грешката се логва и се предава нататък; клиентското прекъсване не се преобразува в 500.
- Status-code middleware показва потребителска 404 страница и при неизвестен маршрут, и при `NotFound()` за липсващ запис. `ErrorsController` е достъпен анонимно и работи и при грешка от POST. Отговорите за грешки не се кешират. Старият адрес `/Home/Error` остава използваем и връща 500.
- `FileErrorLoggerProvider` записва Error и Critical съобщения в дневни JSON-lines файлове: `SportsBooking.Web/App_Data/Logs/errors-YYYY-MM-DD.log` (UTC). Файловете са извън `wwwroot`. Папката се създава автоматично; процесът трябва да има право за запис. При файлов проблем има съобщение в стандартния поток за грешки, без да се подменя оригиналната грешка. Настройката е `FileLogging:Directory` в `appsettings.json`. Console логването е запазено. Логват се и неуспехи при инициализацията на базите.

## Изпълнени проверки

- .NET SDK 9.0.306; target framework net9.0.
- `dotnet build SportsBooking.sln`: успешно в Debug, 0 грешки.
- `dotnet test SportsBooking.sln`: **38 passed, 0 failed, 0 skipped**.
- В ограничената изпълняваща среда build е стартиран с `-m:1 -p:UseSharedCompilation=false --disable-build-servers`; стандартните команди по-долу са подходящи за локална разработка.
- Съществуващият `SixLabors.ImageSharp 4.1.3` издава предупреждение за липсващ Six Labors лиценз при Debug. Съобщението на пакета изисква валиден лиценз за Release; зависимостта не е сменяна и лиценз не е добавян. Следователно тук е потвърден Debug build, а не Release publish.
- В тази среда няма работещ SQL Server. Не са изпълнявани крайни потребителски сценарии срещу реална SQL Server база, нито тест с конкурентни SQL връзки. Транзакционното поведение на услугата е проверено с Moq, а HTTP страниците — чрез TestServer. Това не замества SQL Server интеграционна проверка.
- Двете задания са реализирани. Горните ограничения описват обхвата на извършената проверка.

Реалните build/test изходи и машинно четимият TRX отчет са в `docs/verification/`.

## Стартиране

1. Инсталирайте .NET 9 SDK и SQL Server/LocalDB.
2. Следвайте `docs/SQL_SERVER_SETUP_BG.md` и изпълнете предоставените SQL скриптове. Ако базата вече е подготвена за предходното задание, не я пресъздавайте; тези промени не изискват промяна на схемата.
3. Проверете двете connection strings в `SportsBooking.Web/appsettings.json`.
4. От папката със solution-а изпълнете:

```powershell
dotnet restore SportsBooking.sln
dotnet build SportsBooking.sln
dotnet test SportsBooking.sln
dotnet run --project SportsBooking.Web --launch-profile SportsBooking.Web
```

За тестовете не е необходим SQL Server. За самото приложение е необходим, както и в първоначалния проект. Съществуващите Development демо акаунти и настройките им са запазени.
